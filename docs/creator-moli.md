# Creator Moli V1 — private creator notebooks

## Architecture decision
MoliVerse is a Next.js static export, not a server rendering API host. Its existing ImmersiveStudio sends structured scene edits to immersive-author; course-architect creates multi-lesson blueprints. Neither is a private, open-ended brainstorming session. The existing teacher_dna record is an optional teaching default; courses and course_collections are publication-oriented. We do not alter those records, retrofit the public child chat, or treat an AI output as a published course.

The /teach/creator/ route, linked from /teach/, uses the official moli-cutout.png and existing Supabase Auth session. The browser calls a single Supabase Edge Function. The access gate requires a valid JWT with **admin-managed app_metadata.creator_moli_adult exactly true**. A self-selected teacher role, user_metadata, a checkbox or a public key cannot grant eligibility. A trusted adult identity/eligibility review must occur outside this app before granting access. No grant is created by this migration.

[OpenAI Agents SDK](https://developers.openai.com/api/docs/guides/agents/sdk) offers a runtime for tools/handoffs. [OpenAI runtime comparison](https://developers.openai.com/api/docs/guides/agents) distinguishes direct Responses integration from that orchestration. For this single-agent release we chose application-owned orchestration with the **existing server-side DeepSeek integration**, not an SDK dependency or an additional OpenAI processor. Two calls per chat turn: a streamed short reply and a validated sparse board extraction. Outline/review each make one structured call. No browser key, hosted model memory, background agent, or autonomous publish tool.

## Product / state
One notebook is one persistent session and project: revision, creator-selected stage, message history, confirmed board, unconfirmed suggestions, optional proposed outline, immutable saved versions and review tied to a version. A user need not complete a stage to switch; an existing external course can be entered and reviewed immediately. There is no network call requiring a file or platform-created lesson: paste short authorised extracts or enter an external draft manually. No binary upload, third-party crawl or vector store.

The curated notes in agent.ts are selected by request/topic/stage. Only the owner's teaching style and values plus necessary project data, latest draft and last 12 messages go to DeepSeek. Full history is kept in the private notebook. Treat quoted materials as untrusted. Suggestions never become confirmed facts without an explicit user edit. Version creation keeps old edits; reviewing never approves. Submission locks a specific version into the staff queue without adding a public record.

## Server tool contracts (POST creator-moli; JSON)
All tools require the verified adult session. Project operations use projectId (UUID); mutations also require the exact revision. No ownerId is accepted as identity. HTTP 400 invalid arguments, 401 missing/expired token, 403 ineligible account, 404 missing/not owned, 409 stale/locked project, 429 hourly budget, 502 provider/stream error, 503 storage/configuration. After stream headers, a failure is an error event, not a successful saved reply. Reload if the final saved revision is uncertain.
- list {} → projects: title/id/revision/update time for the owner. create {title} → private project.
- get_creator_context {} → dna (optional own teaching defaults); get_project_state {projectId} → project. Both read-only.
- save_brainstorm_state {edit:{confirm?:partial board, dismiss?:field, stage?:stage}} → updated project. Values and field names validated.
- chat {message} → SSE delta text, then project snapshot or error. Only reply + suggestions persist on successful compare-and-swap. It cannot call publish/save/confirm on the user's behalf.
- generate_course_outline {request?:string} → project with an editable proposal. Does not replace saved versions.
- save_course_draft {draft} → project with an appended version; invalidates earlier review. See lib/creator/workflow.ts for bounded required fields.
- review_course_draft {} → project with advisory strengths, concerns, nextStep for the latest saved version.
- submit {} → locked project plus atomic private submission. Staff review the queue using privileged tooling. No public listing or notification.
- All mutations record revision/action only in the audit log (project creation is represented by its owner row). Rate budget is 60 attempted mutations per owner per UTC DB hour including non-AI edits; 200 messages, 40 saved versions per notebook. Adult conversation and supplied materials may contain private information: explain provider processing to creators, avoid personal details, and establish retention/deletion procedures before wider rollout. Text filters and human review do not guarantee compliance.

## Staging setup (not performed automatically)
1. Apply supabase/creator-moli.sql to a **staging** Supabase project as migration owner. Private tables with RLS + revoked client grants; privileged server writes check owner/revision. Queue and audit written atomically. Admins can query creator_moli_submissions to locate project/state. Do not grant anonymous/reviewer-wide frontend access.
2. Configure the existing DEEPSEEK_KEY as a server secret (optional CREATOR_MOLI_MODEL). Standard Supabase URL and service-role secret are required on the Edge host. Deploy **only** creator-moli to the intended staging project. No key in NEXT_PUBLIC_* or Git.
3. Using trusted Supabase admin tooling, grant app_metadata.creator_moli_adult=true only to a verified eligible adult. Keep existing metadata. Sign out/in to refresh the session. The static site's Supabase URL must match that deployment; this repo currently points to its existing project.
4. npm ci; npm run dev; open /teach/creator/. Do not point production users to staging accidentally. Test invitation denial, tenant isolation, and provider streaming with a real invited staging account before publishing this feature.
5. Try: create “Ferry sketchbook”; describe one memory → inspect a suggestion → change and confirm the topic → outline → edit and save v1 → reload → review → submit. Try saving v2 after v1 review: submission is disabled until v2 is reviewed.

## Verification and evaluation
npm run test:creator mocks auth, DB and provider, but executes the real endpoint, runtime validators, streaming parser and orchestrator. Ten distinct scenario inputs verify ownership, context continuity, confirmation, retries, quotas and no publication. These tests do NOT demonstrate live response quality. The supplied live eval runner (scripts/eval-creator-moli.cjs) uses synthetic data and requires explicit RUN_CREATOR_LIVE_EVAL=yes and a staging key. Score each output against its case criterion, intent preservation, factual caution and question count; mark pass/fail with evidence. Run again after instruction changes. Do not evaluate with children's transcripts.
Optional scripts/test-creator-moli-sql.cjs exercises real PostgreSQL semantics in disposable PGlite via NODE_PATH; scripts/test-creator-moli-browser.cjs exercises the static export in Chrome at 1300 and 390 pixels with isolated auth/provider doubles via Playwright. Neither dependency ships to browsers. Production accounts, cloud migration/deployment, staff adjudication UI, review turnaround and live model relevance are not covered by those checks.
